# RAG Document Q&A System — Llama 2

A Retrieval-Augmented Generation (RAG) system that lets you upload PDF, DOCX,
or TXT documents and ask questions about them in natural language. Answers
are generated by Llama 2, grounded in the specific text retrieved from your
documents, rather than the model's general training knowledge.

---

## 1. Why RAG instead of just asking Llama 2 directly?

A standalone LLM answers from what it memorized during training. That means:

- It knows nothing about documents that didn't exist when it was trained
  (your company reports, your course notes, today's PDF).
- It can **hallucinate** — produce a fluent, confident-sounding answer that's
  factually wrong, because it has no way to check itself against a source.

RAG fixes both problems by inserting a **retrieval step** before generation:
the system first searches your documents for the passages most relevant to
the question, then gives the LLM those passages as context and instructs it
to answer *only* from that context. This is why RAG answers are more
accurate and traceable (you can show exactly which passage backs up the
answer) than a standalone LLM.

                            │

## 3. Project structure

```
rag_project/
├── app.py                  # Streamlit frontend — wires all 5 steps together
├── requirements.txt
├── src/
│   ├── config.py            # every tunable setting, in one place
│   ├── ingestion.py          # Step 1: extract + chunk text
│   ├── embed_index.py        # Step 2: embeddings + FAISS index
│   ├── retrieval.py          # Step 3: similarity search + context formatting
│   ├── generation.py         # Step 4: Llama 2 prompting + generation
│   └── evaluate.py           # Step 5: BLEU / ROUGE-L / embedding similarity
└── sample_docs/             # put test PDFs/DOCX/TXT here
```

Each module maps 1:1 onto a step in the project brief. That's a deliberate
design choice: it makes the codebase easy to explain (and to defend in a
viva) because the file structure *is* the architecture.

## 4. Step-by-step explanation

### Step 1 — Data Ingestion (`src/ingestion.py`)

- **PDFs** are read with **PyMuPDF** (`fitz`), page by page. PyMuPDF was
  picked over PDFPlumber for speed on large files; PDFPlumber is the better
  choice if you specifically need table extraction.
- **DOCX** files are read with **docx2txt**.
- **TXT** files are read directly.
- The extracted text is then **chunked** into ~1000-character windows with a
  150-character overlap (`chunk_text()`).
  - *Why chunk at all?* Embedding an entire document as one vector would mix
    together every topic in it, so a search for one specific fact would
    match poorly. Chunking keeps each vector focused on one idea.
  - *Why overlap?* Without overlap, a sentence or idea that happens to fall
    exactly on a chunk boundary gets split in two and loses meaning in both
    halves.

### Step 2 — Embeddings & Indexing (`src/embed_index.py`)

- Each chunk is converted into a 384-dimensional vector using
  **`sentence-transformers/all-MiniLM-L6-v2`** — small, fast, CPU-friendly,
  and normalized so that inner product = cosine similarity.
- Vectors are stored in a **FAISS** `IndexFlatIP` (exact inner-product
  search). FAISS was chosen over ChromaDB/Pinecone because it needs no
  external service or account and is fast enough for a project-scale corpus
  (thousands of chunks). At production/multi-million-vector scale you'd swap
  in an approximate index (`IndexIVFFlat`, `IndexHNSW`) or move to a managed
  service like Pinecone.
- The index and chunk metadata are persisted to disk (`save`/`load`) so
  documents don't need to be re-embedded on every restart.

### Step 3 — Query Processing & Retrieval (`src/retrieval.py`)

- The user's question is embedded with the **same** model used for the
  documents (this consistency is essential — you can't compare vectors from
  two different embedding spaces).
- FAISS returns the **top-k** most similar chunks by cosine similarity.
- The chunks are formatted into a labelled context block (source file +
  chunk number + similarity score) so the answer can be traced back to
  specific passages.

### Step 4 — Response Generation (`src/generation.py`)

- The context block + question are wrapped in Llama-2's official chat
  prompt format (`[INST] <<SYS>> ... <</SYS>> ... [/INST]`).
- The system prompt explicitly instructs the model to answer **only** from
  the given context and to say it doesn't know rather than guess. This
  prompt-engineering step is what actually makes the system "retrieval
  augmented" rather than just a chatbot with some extra text pasted in.
- **4-bit quantization** (via `bitsandbytes`) is used when a GPU is
  available, shrinking Llama-2-7b from ~13GB to ~4–6GB of VRAM.
- Because Llama-2-7b-chat-hf is **gated** (Meta requires a Hugging Face
  account, an approved access request, and a token) and needs a GPU to run
  at a usable speed, the code automatically falls back to
  **TinyLlama-1.1B-Chat** (ungated, CPU-runnable) if Llama-2 can't be
  loaded. The rest of the pipeline is unchanged — only the generator model
  swaps.

### Step 5 — Evaluation & Optimization (`src/evaluate.py`)

Three metrics, each catching something the others miss:

| Metric | Type | Rewards | Blind spot |
|---|---|---|---|
| BLEU | precision, n-gram overlap | exact wording matches | penalizes correct answers phrased differently |
| ROUGE-L | recall, longest common subsequence | content coverage | still lexical, not semantic |
| Embedding cosine similarity | semantic | meaning match regardless of wording | says nothing about fluency/factual precision |

Reporting all three avoids over-trusting any single number — a common
weakness in evaluation write-ups examiners look for.

## 5. Setup & running it

```bash
# 1. Create environment
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate

# 2. Install dependencies
pip install -r requirements.txt

# 3. (Only if you have Llama-2 access) request access at:
#    https://huggingface.co/meta-llama/Llama-2-7b-chat-hf
#    then generate a token at https://huggingface.co/settings/tokens

# 4. Run the app
streamlit run app.py
```

In the app:
1. Upload documents in the sidebar → click **Process & Index Documents**.
2. Enter your HF token (optional — leave blank to use the fallback model)
   and click **Load Llama 2 (or fallback)**.
3. Ask questions in the chat box. Expand "Show retrieved sources" under any
   answer to see exactly which chunks were used.
4. Optionally paste a ground-truth answer in the evaluation panel to score
   the last answer with BLEU/ROUGE-L/embedding similarity.

**Hardware note:** Llama-2-7b in 4-bit needs roughly a 6GB+ VRAM GPU (e.g. a
free-tier Colab T4 works). Without a GPU or without HF access, the app
automatically uses TinyLlama-1.1B on CPU so you can still demo the full
pipeline.

  using the real `VectorStore`/FAISS code path with mocked embedding

the real embedding model and Llama-2/TinyLlama automatically on first use —
no code changes needed.

## 7. Possible extensions (mention these if asked "how would you improve it")

- Sentence/paragraph-aware chunking (e.g. LangChain's
  `RecursiveCharacterTextSplitter`) instead of raw character windows.
- A re-ranking step (e.g. a cross-encoder) after the initial FAISS search,
  to improve precision of the top-k results.
- Streaming token-by-token generation in the UI instead of waiting for the
  full response.
- Swapping FAISS for ChromaDB to get persistent metadata filtering (e.g.
  "only search within document X"), or Pinecone for a managed, multi-user
  deployment.
- Fine-tuning (vs. the prompt-engineering used here) if you had a large
  labelled Q&A dataset specific to your domain.

## 9. Viva prep — likely questions and how to answer them

**Q: What does "Retrieval-Augmented" actually mean?**
A: The LLM's generation is *augmented* with retrieved external documents at
inference time, instead of relying solely on knowledge baked into its
weights during training. Retrieval happens first, generation happens
second, conditioned on what was retrieved.

**Q: Why chunk documents instead of embedding the whole document as one
vector?**
A: A single vector for a whole document averages together every topic in
it, destroying the fine-grained meaning needed for accurate similarity
search. Chunking keeps each vector focused on one coherent idea so
retrieval can pinpoint the exact relevant passage.

**Q: Why did you pick FAISS over ChromaDB or Pinecone?**
A: FAISS runs fully locally with no external account/service, is very fast
for exact search at this project's scale, and is the simplest to set up.
ChromaDB adds a persistent DB layer with metadata filtering; Pinecone is a
managed cloud service better suited to production/multi-user scale — good
answers if asked "what would you use at scale."

**Q: Why cosine similarity and not Euclidean distance?**
A: Embeddings encode meaning as *direction* in vector space; two chunks
about the same topic point the same way even if their magnitudes differ.
Cosine similarity measures that angle directly. (Implemented here as inner
product on L2-normalized vectors, which is mathematically the same thing.)

**Q: Is this fine-tuning or prompt engineering?**
A: Prompt engineering — no model weights are changed. The system prompt
restricts Llama 2 to answering from the given context and instructs it to
say "I don't know" instead of hallucinating. Fine-tuning would mean further
training on a custom dataset, which is unnecessary for this use case since
context injection already grounds the answers.

**Q: What's the point of using three different evaluation metrics?**
A: BLEU and ROUGE-L are lexical (word-overlap) metrics — fast and
standard, but they penalize a correct answer that's simply phrased
differently from the reference. Embedding cosine similarity captures
semantic closeness even when wording differs completely. Using all three
avoids over-trusting any single metric.

**Q: What are the main failure modes / limitations of this system?**
A: (1) Retrieval quality caps generation quality — if the wrong chunk is
retrieved, the LLM will confidently answer from the wrong context. (2)
Character-based chunking can still split a sentence awkwardly. (3) A small
embedding model (MiniLM) trades some retrieval accuracy for speed. (4)
Llama-2-7b-chat is a relatively small LLM and can still make reasoning
errors even with perfect context.

**Q: How would you scale this to millions of documents?**
A: Swap `IndexFlatIP` (exact search) for an approximate index like
`IndexIVFFlat` or `IndexHNSW`, or move to a managed vector DB like Pinecone;
also consider batching embedding generation and sharding the index across
machines.
